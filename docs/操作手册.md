## 1. 系统是什么

**一句话**：境内服务器上的一个 HTTP 服务，让十几二十个人通过手机 App 把「一段文本」或
「一个网址」交给智能体，拿回一份摘要。

**交付物是一套 API，没有界面。** App 由其他人开发，所以本项目的产出是纯后端服务 +
接口文档 + 联调沙箱；手机端的一切不在范围内。

只有两类业务动作：

| 场景 | 输入 | 智能体做什么 |
|---|---|---|
| 链接摘要 | 一个 URL | 用 `webfetch` 抓取网页 → 总结 |
| 文本摘要 | 一段文本 | 直接总结 / 改写 / 提炼要点 |

**不做**：代码开发、文件协作、知识库检索、多人协同、App 界面。

引擎用的是 **opencode**（开源终端 AI 智能体），通过它的 HTTP 服务模式
（`opencode serve`）调用。一个关键前提必须先知道：**opencode 服务端没有用户体系**，
只有一把 HTTP Basic 账号密码，而且它的 `/session` 接口返回**全局**会话列表、无法按用户
过滤。因此**身份认证与越权防护必须 100% 由网关承担**，opencode 只能待在内网。

## 2. 架构

### 2.1 一张图

```
   第三方 App（他人开发，只调 API）
        │
        │  HTTPS 443 + Bearer Token          ← 全项目唯一对外的门
        ▼
┌──────────────────────────────────────────────────────┐
│ nginx（唯一映射端口的容器：80 / 443）                  │
│  TLS 终止 · 限流（按凭证分桶）· SSE/WS 不缓冲          │
└───────────────┬──────────────────────────────────────┘
                │  http://gateway:8080
                ▼
┌──────────────────────────────────────────────────────┐
│ gateway（FastAPI，必须单 worker）                      │
│   auth      身份、Token 签发、配额                     │
│   tasks     任务表 + 每用户队列 + 公平派发             │
│   pool      实例池：谁闲、谁忙、谁挂了                  │
│   relay     每个实例一条 /event，按 sessionID 扇出      │
│   callback  任务完成后回调 App 服务端（HMAC 签名）      │
│   存储       SQLite（命名卷 gateway-data）             │
└──────┬─────────────────────────────────┬─────────────┘
       │                                 │ 回调（可选）
       │  http://opencode-N:4096         ▼
       │                          App 的服务端
       ▼
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ opencode-1   │ │ opencode-2   │ │ opencode-3   │  ← 实例池
│ 卷 oc1-data  │ │ 卷 oc2-data  │ │ 卷 oc3-data  │
│ 三实例共享同一个 workspace 卷                     │
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       └────────────────┴────────────────┘
                        │ OpenAI 兼容协议
                        ▼
              模型服务（MODEL_BASE_URL）
     生产：真实厂商  │  演练：mock-model（内网，无端口）
```

六个容器：`nginx`、`gateway`、`opencode-1/2/3`、`mock-model`。

### 2.2 暴露面：只有 nginx 能见公网

| 容器 | 宿主端口 | 谁能访问 | 说明 |
|---|---|---|---|
| `nginx` | **80 / 443** | 公网 | 唯一入口 |
| `gateway` | 无 | 只有 nginx | 业务逻辑与鉴权都在这里，**它才是真正的攻击面** |
| `opencode-1/2/3` | 无 | 只有 gateway | 每个实例一把独立随机密码 |
| `mock-model` | 无 | 只有 opencode | 演练用假模型，**不能用于生产** |

`gateway` 和 `opencode` 都没有 `ports:`，**宿主机也连不上**，只能走 compose 内部网络。
服务器/安全组只需放行 80、443（和你的 SSH 端口）。

> **别把「端口不暴露」当成「不是攻击面」**：外部请求最终一定会穿过 nginx 到达 gateway，
> 越权校验、入参长度限制、prompt 注入防护、配额限制一个都不能省。

### 2.3 请求怎么走

1. App 拿 Token（模式 A 账密，或模式 B 服务端签名直传），`POST /api/v1/tasks` 提交任务。
2. gateway 落库（`tasks` 表，状态 `queued`），放进**该用户的队列**。
3. **dispatcher** 每 0.5 秒一轮：挑一个空闲实例 → 在其上建会话（或复用该用户的粘性会话）
   → 下发 `prompt_async`，带上 `{providerID, modelID}` 与工具白名单。
4. opencode 干活（必要时调 `webfetch` 抓网页），模型产出内容。
5. gateway 维持**每个实例一条** `/event` 上游连接，把事件按 `sessionID` 扇出给对应任务；
   App 通过 SSE（`GET /api/v1/tasks/{id}/events`）或 WebSocket（`/api/v1/ws/tasks/{id}`）
   拿增量。
6. 结束：状态落 `succeeded` / `failed` / `timeout` / `canceled`，按需回调 App 服务端。

### 2.4 实例池与调度

**为什么不是单个 opencode 进程**：它的 `/session` 全局可见，网关一旦有 bug 就是
「A 能读到 B 的对话」；而且一个长任务会拖慢同进程内所有人。拆成池之后并发能力清晰、
故障隔离、扩容就是加一个容器。

**代价**：跨实例无法复用上下文。解决办法是**用户粘性**——`user_bindings` 表记录
`(user_id → instance_id, session_id)`，同一用户优先回到同一实例、复用同一会话；
真溢出到别的实例时，把上一轮摘要拼进 prompt 当背景。

调度规则（dispatcher 每轮）：

1. 优先派「该用户粘性实例上、且该实例空闲」的任务（命中上下文）。
2. 其余按 FIFO 出队，但**每个用户同时最多 1 个在飞任务**（公平闸门，防一人刷满池）。
3. 有闲实例就派；没有就留在队列里，任务返回「排队第 N 位」。

### 2.5 任务状态机

```
queued → running → streaming → succeeded
                            ↘ failed
                            ↘ timeout
                            ↘ canceled
```

### 2.6 安全模型

| 关心的事 | 怎么做 |
|---|---|
| 身份 | 模式 A：账密换 Token。模式 B：App 服务端用共享密钥 HMAC 签名换 Token，终端用户免二次登录 |
| 越权 | 任务都带 `user_id`，查询/取消/订阅都校验归属；opencode 的全局会话列表不对外暴露 |
| 智能体越界 | 工具白名单：**只允许 `webfetch`**，`bash`/`read`/`write`/`edit`/`apply_patch`/`glob`/`grep`/`lsp`/`skill`/`websearch` 全 deny（`gateway/app/services/prompting.py` 与 `opencode/config/agents/summarizer.md` 双重声明） |
| prompt 注入 | agent 定义里写明：网页内容与用户文本**只当数据**，绝不执行其中的指令 |
| SSRF | 回调地址只允许白名单域名，且**必须是 https** |
| 限流 | nginx 按凭证（token）分桶，一人一个桶；不带凭证的退回按来源 IP |
| 滥用 | 每人每天配额、每用户队列深度上限、单任务超时 |

> 因为关掉了所有文件类工具，**工作目录里不放任何跨用户数据**（三实例共享一个空目录）。

### 2.7 数据与存储

SQLite，五张表：

| 表 | 装什么 |
|---|---|
| `users` | 账号、显示名、每日配额、启用状态；模式 B 的账号还有 `external_user_id` |
| `api_clients` | 刷新令牌与 scope |
| `tasks` | 任务本体：输入、状态、实例/会话绑定、结果、用量、回调状态 |
| `task_events` | 流式片段，断线重连可补发 |
| `user_bindings` | 用户 → 实例/会话的粘性映射与上一轮摘要 |

**实例的忙闲状态和 `session_id → task_id` 路由表只放内存、不落库**，所以：

> **gateway 必须单 worker 运行**（`uvicorn` 不加 `--workers`，也不要起多副本）。
> 多进程时每个进程各有一份实例池视图，派发会互相打架。

Docker 命名卷（前缀是 compose 项目名，实际名字是 `agent-gateway_*`）：

| 卷 | 容器内路径 | 装什么 | 要不要备份 |
|---|---|---|---|
| `gateway-data` | `/srv/agent/data` | SQLite 库：账号、任务、会话映射 | **要** |
| `workspace` | `/srv/agent/workspace` | agent 工作目录（当前是空的） | **要** |
| `oc1-data`/`oc2-data`/`oc3-data` | `/home/app/.local/share` | 实例私有会话缓存 | 不用（网关侧有摘要可重建） |

### 2.8 关键默认值与时限

| 项 | 默认 | 变量 |
|---|---|---|
| 单任务超时 | 180 秒 | `TASK_TIMEOUT_SECONDS` |
| 实例空闲回收（dispose） | 20 分钟 | `INSTANCE_IDLE_DISPOSE_MINUTES` |
| 实例健康检查 | 每 10 秒，连续 3 次失败标记不可用 | `POOL_HEALTH_INTERVAL_SECONDS` / `POOL_HEALTH_FAILURE_THRESHOLD` |
| dispatcher 轮询 | 0.5 秒 | `DISPATCHER_INTERVAL_SECONDS` |
| 每人每天配额 | 30 | `DEFAULT_DAILY_QUOTA` |
| 每人同时在飞任务 | 1 | `MAX_IN_FLIGHT_PER_USER` |
| 每用户队列深度 | 3（超出 429） | `MAX_QUEUE_DEPTH_PER_USER` |
| 输入文本上限 | 200,000 字符 | `MAX_TEXT_CHARS` |
| 抓取内容上限 | 20,000 字符 | `MAX_FETCH_CHARS` |
| 输出上限 | 4,000 字符 | `MAX_OUTPUT_CHARS` |
| 结果保留 | 30 天 | `RESULT_RETENTION_DAYS` |
| Access Token 有效期 | 12 小时 | `ACCESS_TOKEN_TTL_SECONDS` |
| Refresh Token 有效期 | 30 天 | `REFRESH_TOKEN_TTL_DAYS` |

## 3. 从零开始构建

从一台空机器到手机能用。**每一步都有验证命令，验不过别往下走**——这个项目里
「容器 healthy」和「真的能用」是两件不同的事（模型配错、名册漏改、`engine: ready`
都出现过「看起来正常但实际不可用」）。

### 3.1 动手前先定下来

| 项 | 建议 | 为什么 |
|---|---|---|
| 服务器 | 4 vCPU / 4 GB 起步，**推荐 8 GB**，至少加 2 GB swap | 每个 opencode 实例是一个 Node 进程；4 GB 跑 3 实例没 swap 会吃紧 |
| 系统盘 | ≥ 40 GB | 镜像约 2.5 GB + 构建缓存 1.3 GB + 数据 |
| 系统 | Ubuntu 22.04 / 24.04 | 演示环境是 24.04，其他发行版未验证 |
| 域名 | **已备案** | 境内服务器上未备案域名走 80/443 会被拦 |
| 安全组 | 只放行 80、443（加 SSH） | gateway / opencode 都没有映射端口，不需要开 |
| TLS 证书 | 正式证书 → `certs/fullchain.pem`、`certs/privkey.pem` | `nginx.conf` 强制 TLS，证书缺失时 nginx 直接启动失败 |

### 3.2 装 git 和 docker

```bash
sudo apt-get update && sudo apt-get install -y git
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker "$USER" && newgrp docker    # 免 sudo；重登一次才彻底生效
docker compose version                              # 需要 v2：命令是 docker compose
```

**新机器上不需要自己装 opencode，也不需要 node / npm / python。** opencode 由
`opencode/Dockerfile` 在构建期从 npm 装进镜像，版本钉在 `ARG OPENCODE_VERSION`。
宿主机只需要 `git` + `docker`。

配镜像加速器（境内必做，`registry-1.docker.io` 直连超时）：

```bash
sudo tee /etc/docker/daemon.json >/dev/null <<'JSON'
{
  "registry-mirrors": ["https://docker.m.daocloud.io"]
}
JSON
sudo systemctl restart docker
docker info | grep -A2 'Registry Mirrors'    # 确认生效
```

镜像**内部**的依赖下载已走国内源（opencode 用 `registry.npmmirror.com`，Python 用清华 PyPI）。

### 3.3 把代码和镜像弄到机器上

**方式 A：机器能上外网** —— 直接克隆，构建时联网拉依赖：

```bash
git clone https://ghfast.top/https://github.com/zhliu577-a11y/QinAN.git
cd QinAN/deploy
```

直连 GitHub 不通就用上面的加速前缀（另有 `ghproxy.net` 可用）。

**方式 B：机器不能上外网** —— 在别的机器上构建好，把镜像打包带过去：

```bash
# 在能上网的机器上：克隆并完整构建过一次，再打包镜像
git clone https://ghfast.top/https://github.com/zhliu577-a11y/QinAN.git
cd QinAN/deploy && docker compose up -d --build
docker save agent-opencode:local agent-gateway:local agent-mock-model:local \
            nginx:1.27-alpine -o qinan-images.tar

# 把整个 QinAN 目录和 qinan-images.tar 拷到新机器（U 盘 / scp 都行）

# 新机器上
cd QinAN/deploy
docker load -i /path/to/qinan-images.tar   # 期望 4 行 Loaded image
docker compose up -d                       # 注意：不带 --build
```

实测过的几点：

- 四个镜像共 **361 MB**，`docker save` 成单个 tar 是 **321 MB**；代码只有 840 KB（58 个文件）。
- **tar 不用再 gzip**：Docker 层本身已压缩，实测 321 → 319 MB，白费时间。
- 只拷 `deploy/` 目录也够——`build:` 的 context 不存在时，`up -d`（不带 `--build`）
  照样工作，compose 直接用已有镜像。但仍建议整个仓库拷过去，方便以后改配置。
- 方式 B 之后**别再用 `up -d --build`**，那会重新走构建、又需要联网。

### 3.4 写 `.env`

```bash
cp .env.example .env
chmod 600 .env        # 里面有 JWT 和实例密码
```

**必改项**（其余保持默认）：

| 变量 | 填什么 | 生成方式 |
|---|---|---|
| `PUBLIC_BASE_URL` | `https://你的域名` | —— |
| `JWT_SECRET` | 随机 | `openssl rand -hex 32` |
| `ADMIN_TOKEN` | 随机 | `openssl rand -hex 24` |
| `OC1_PASSWORD` / `OC2_PASSWORD` / `OC3_PASSWORD` | 三把**互不相同**的随机值 | 各 `openssl rand -hex 24` |
| `CALLBACK_HMAC_SECRET` | 随机；完全不用回调可以不管 | `openssl rand -hex 32` |
| `CALLBACK_ALLOWED_HOSTS` | App 后端域名，逗号分隔；**只允许 https，留空会拒掉所有回调** | —— |
| `EXCHANGE_HMAC_SECRET` | 只有用模式 B 才填，与 App 团队约定同一个值 | `openssl rand -hex 32` |
| `MODEL_*` | 见 3.7 | —— |

再确认三项：

- `MOCK_MODE=false` —— 保持 false
- `DEFAULT_DAILY_QUOTA` —— 每人每天任务条数
- `CORS_ALLOW_ORIGINS` —— 原生 App 留空；H5 / WebView 填来源域名

`.env` 里的变量是**分给两边**的：配额/限流/回调/JWT 只影响 gateway；
`MODEL_BASE_URL`/`MODEL_API_KEY` 只影响 opencode；`MODEL_PROVIDER`/`MODEL_NAME` 两边都读。

### 3.5 放证书

```bash
mkdir -p certs
# 放成这两个文件名（nginx.conf 里写死的）：
#   certs/fullchain.pem
#   certs/privkey.pem
```

没有域名时只能用自签证书演练：`./gen-self-signed-cert.sh <IP或域名>`。
自签会让 App 报证书不受信任，**不要用于生产**。

### 3.6 首次构建与启动

```bash
docker compose config >/dev/null && echo "语法 OK"
docker compose up -d --build        # 首次要构建三个镜像，慢是正常的
docker compose ps                   # 六个容器都应是 healthy
```

```bash
curl -s https://你的域名/healthz            # 期望 ok（nginx 自己的探针）
curl -s https://你的域名/api/v1/health      # 期望 engine: ready
docker compose logs --tail 50 gateway
```

> `/api/v1/health` 的 `engine: ready` **只说明三个 opencode 实例在，不代表模型能用**。
> 模型配错时这个接口照样绿，要等第一个任务失败才暴露。

### 3.7 接真实模型

默认值指向内置模拟模型（演练用）。换成真实服务商只改四行：

```
MODEL_PROVIDER=deepseek
MODEL_NAME=deepseek-chat
MODEL_BASE_URL=https://api.deepseek.com/v1
MODEL_API_KEY=sk-真实密钥
```

模型这件事被切成两半，**改完重建谁取决于你改了哪一半**：

| 谁 | 决定什么 | 读哪些变量 |
|---|---|---|
| `gateway` | 问哪个模型（每个任务下发 `{providerID, modelID}`） | `MODEL_PROVIDER`、`MODEL_NAME` |
| `opencode` | 问到哪、用什么密钥 | `MODEL_BASE_URL`、`MODEL_API_KEY` |

所以改完 `.env` 要**不点名**地重建，一次就够：

```bash
./ops.sh apply          # 等价于 docker compose up -d（不点名，compose 自己算该重建谁）
docker compose ps       # 等六个都 healthy 再提交任务
```

> **别点名服务、别加 `--force-recreate`**。点名后 compose 只处理点到的那几个，
> 没点到的即使配置变了也不动——实测过：改了 `MODEL_NAME` 只重建 opencode，
> gateway 会一直用它启动时那份配置，**照样发旧的 model id，而且不报任何错**。
> 真实服务商下的症状是「换了模型但账单毫无变化」。

`MODEL_NAME` 必须是**该地址真实提供的 id**（写错启动时不报错，第一次调用才失败）。
查实际有哪些模型：

```bash
docker compose exec opencode-1 sh -c \
  'curl -s -H "Authorization: Bearer $MODEL_API_KEY" "$MODEL_BASE_URL/models"'
```

**连通性自测**——两层，都能验：

```bash
# 第一层：从实例内直接打模型端点（不经过网关，能区分问题在模型侧还是链路侧）
docker compose exec opencode-1 sh -c \
  'curl -s -X POST "$MODEL_BASE_URL/chat/completions" \
     -H "Authorization: Bearer $MODEL_API_KEY" -H "Content-Type: application/json" \
     -d "{\"model\":\"deepseek-chat\",\"messages\":[{\"role\":\"user\",\"content\":\"Reply with exactly: PONG\"}]}"'

# 第二层：走完整链路提交一个真实任务，status=succeeded 且 result_md 有内容即通过
```

> **不要用 `docker compose exec opencode-1 opencode run --model ... '...'` 做自测**：
> 实测它在非 TTY（脚本 / ssh / CI）下会**挂住不返回**——`timeout` 到点被杀、退出码 124、
> 零输出，而 opencode 日志显示模型调用其实成功了。请求确实到了模型端，是 CLI 不吐结果，
> 拿它判断「模型配错」会直接误判。上面第一层的 curl 是等价且可靠的替代。

换**服务商**（改 `MODEL_PROVIDER` 的取值）还要动 `opencode/config/opencode.json` 里
覆写的那个 provider 键名（当前是 `deepseek`），两处必须同名，然后
`docker compose up -d --build opencode-1`。

### 3.8 开户

库里没有账号时无法登录，先用管理接口开一个。`/internal/*` 在 nginx 上是 `deny all`，
**必须从容器内打**：

```bash
ADMIN_TOKEN=$(grep ^ADMIN_TOKEN= .env | cut -d= -f2-)
docker compose exec gateway curl -s -X POST http://127.0.0.1:8080/internal/users \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"zhangsan","password":"换成强密码","display_name":"张三","daily_quota":30}'
```

模式 B（App 侧可信直传）由 `/api/v1/auth/exchange` **自动开户**，不用手工开。

> **没有「用户自助改密码」接口**。改密码只能走管理接口：
> `PATCH /internal/users/{id}`，body `{"password":"新密码"}`。所以密码要在开户后立刻
> 设成最终值再交给本人，重置也由运营方执行。要终端用户能自己改，需与 App 团队一起加接口。

## 4. 日常使用

### 4.1 一个入口：`ops.sh`

日常运维只用一个脚本，跑在宿主机上、在 `deploy/` 目录里执行。它把容易记错的细节
都固化好了（比如「重建」一律用 `--force-recreate` 而不是 `restart`）。

```bash
./ops.sh status                  # 先看这个：容器 + 对外健康 + 网关自检
./ops.sh health                  # 只输出 ok/degraded，退出码即状态，给监控用
./ops.sh apply                   # 把 .env 的改动落地
./ops.sh instances               # 每个实例忙不忙、失败几次、挂了几个会话
./ops.sh logs gateway -f         # 跟容器 stdout；服务名可换 nginx/opencode-1
./ops.sh logs-api --level error  # 网关进程自己的近期日志
./ops.sh user zhangsan           # 单用户：配额用量、任务分布、设备、实例绑定
./ops.sh users                   # 用户列表
./ops.sh metrics                 # 池与队列指标
./ops.sh restart gateway         # 点名重建（gateway|nginx|opencode|all）
./ops.sh heal                    # 只重建不健康的容器
./ops.sh shell gateway           # 进容器
./ops.sh backup                  # 备份两个数据卷
./ops.sh help                    # 全部命令
```

### 4.2 看状态

先 `./ops.sh status`。要细看实例，用 `./ops.sh instances`——排查「任务卡住」时先看这里：

| 字段 | 含义 | 怎么读 |
|---|---|---|
| `status` | `idle` / `busy` / `unhealthy` | `busy` 且 `busy_seconds` 很大 → 该实例卡死或模型端不返回 |
| `failures` | 连续健康检查失败次数 | 到 3 就被标 `unhealthy`，任务不再派给它 |
| `sessions` | 该实例上挂着的会话数 | 有会话时不会被空闲回收 |
| `busy_seconds` / `idle_seconds` | 忙/闲了多久 | 配合上面判断 |

### 4.3 用户与配额

```bash
./ops.sh users                   # 列表
./ops.sh user zhangsan           # 详情（也接受用户 ID）
```

改配额、停用账号、重置密码都走管理接口（`/internal/*`，必须从容器内打）：

```bash
ADMIN_TOKEN=$(grep ^ADMIN_TOKEN= .env | cut -d= -f2-)

# 改配额 / 停用 / 改密码
docker compose exec gateway curl -s -X PATCH http://127.0.0.1:8080/internal/users/2 \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"daily_quota":50,"enabled":true,"password":"新密码"}'
```

`daily_quota`、`enabled`、`password` 三个字段都是可选的，只传要改的。

### 4.4 备份与恢复

```bash
./ops.sh backup                  # 备份 gateway-data 与 workspace，产物在 backup/
```

它会先 `stop gateway`（SQLite 写入过程中被复制会拿到半截状态），备完自动拉起来。

恢复：`docker compose stop gateway` → 把包解回同名卷 → `docker compose up -d gateway`。
卷名带 compose 项目名前缀（`agent-gateway_gateway-data`），用 `docker volume ls` 确认。

> **把 `backup/` 复制到另一台机器。** 备份和业务数据放在同一台机器上不算备份。

### 4.5 App 侧怎么对接

给 App 团队看 `docs/API.md`，重点三件：

- **身份**：模式 A（账密）或模式 B（服务端签名直传，推荐给已有用户体系的 App）。
- **拿进度用 SSE**，`GET /api/v1/tasks/{id}/events`；不要轮询 `GET /tasks/{id}`。
- **429 有两种**：网关返回的是带 `code` 和 `Retry-After` 的 JSON，nginx 返回的是没有
  `Retry-After` 的 HTML 错误页，两者要分开处理。

联调时可以让网关进 `MOCK_MODE=true`（不启动 opencode，直接返回固定样例），
App 侧对接口、SSE、配额都不用等模型。

## 5. 变更手册：改什么用什么命令

**两条前提**：

1. 环境变量只在**容器创建时**注入，`docker compose restart` 读不到新值。
   （「进程自己崩了」这种情况 `restart: unless-stopped` 已经处理，不用手工干预。）
2. **改 `.env` 不要点名服务、不要加 `--force-recreate`**，直接 `docker compose up -d`。
   compose 会把 `env_file` 内容算进每个服务的配置哈希，自己算出该重建谁；
   一旦点名，没点到的服务即使配置变了也不动。

所有命令都在 `deploy/` 目录下执行。

| 你要改的东西 | 命令 | 备注 |
|---|---|---|
| **任何 `.env` 改动**（配额、模型、密码、密钥…） | 改 `.env` → `./ops.sh apply`（= 不点名的 `up -d`） | 一律同一条命令，不用记「谁该重建」 |
| nginx 配置（限流、超时、路由） | 改 `nginx.conf` → `docker compose up -d --force-recreate nginx` | 单文件 bind mount，内容变化 compose **检测不到**，必须强制重建 |
| agent 权限、`agents/*.md`、`opencode.json` | 改文件 → `docker compose up -d --build opencode-1` | 这些**构建进镜像**，`--force-recreate` 不够 |
| opencode 版本 | 改 `opencode/Dockerfile` 的 `ARG OPENCODE_VERSION` → `docker compose up -d --build opencode-1` | 同上 |
| gateway 代码 | 改 `gateway/app/**` → `docker compose up -d --build gateway` | |
| 实例数量 | 改 `docker-compose.yml` 四处（见 `deploy/README.md` 第 8 节）→ `docker compose up -d` | 不用 `--build`，新实例复用现成镜像 |
| 证书 | 覆盖 `certs/*.pem` → `docker compose exec nginx nginx -s reload` | 证书是 bind mount，`reload` 就够（与 `nginx.conf` 不同） |
| 就是想无条件重启某几个服务 | `./ops.sh restart gateway`／`restart opencode`／`restart all` | 点名 + `--force-recreate`，**不用于 `.env` 落地** |

一句话版本：**`.env` → `./ops.sh apply`；镜像里的东西 → `--build`；
`nginx.conf` → `--force-recreate nginx`；证书 → `reload`。**

**改完固定验这三条**：

```bash
docker compose ps                       # 1) 六个容器都 healthy 再继续
curl -s https://你的域名/api/v1/health   # 2) engine: ready，pool_total 等于实例数
ADMIN_TOKEN=$(grep ^ADMIN_TOKEN= .env | cut -d= -f2-)
docker compose exec gateway curl -s -H "X-Admin-Token: $ADMIN_TOKEN" \
  http://127.0.0.1:8080/internal/status | python3 -m json.tool   # 3) config 段 = 网关当前生效配置
```

第 3 条是判断「配置到底生效没有」的权威手段：`config.model_provider` / `config.model_name`
就是网关**此刻**会下发的值，和 `.env` 不一致就说明 gateway 没重建。

**实例开关**：

```bash
docker compose stop opencode-3     # 临时下线：约 30s 后网关标记不可用并停止派活，其余实例照常干活
docker compose start opencode-3    # 恢复：实测约 5s 内回到 idle
```

> 重建实例后 **前 10~30 秒不要提交任务**：池子的健康检查每 10 秒一轮、连续 3 次失败才
> 标记不可用，这段时间网关仍会往还没 bootstrap 完的实例派活，实测会让任务直接 `failed`
> （报错 `创建会话失败 instance=oc-1: All connection attempts failed`）。

## 6. 排错：按症状索引

### 6.1 任务失败或卡住

| 症状 | 先查 | 常见原因 |
|---|---|---|
| 提交就 `failed`，报 `Model not found: provider/model` | `docker compose exec gateway printenv MODEL_NAME` 与 `/internal/status` 的 `config` | `.env` 改了但 gateway 没重建（见第 5 章），或 `MODEL_NAME` 不是该地址真实提供的 id |
| 任务一直是 `queued`，排队位次不动 | `./ops.sh instances` | 所有实例都 `unhealthy`（模型端挂了 / 实例挂了）；或全局队列被前面的人占满 |
| 任务 `running` 很久不动 | `./ops.sh instances` 看 `busy_seconds` | 实例卡死或模型端不返回；到 `TASK_TIMEOUT_SECONDS`（180s）会被回收成 `timeout` |
| `创建会话失败 instance=oc-1: All connection attempts failed` | `docker compose ps` | 实例刚重建、还没就绪。等六个容器都 healthy |
| url 任务 `fetched_chars` 是 `null` | 该 URL 能不能抓 | 抓取失败（域名不存在 / 被墙 / 需要代理）。境外站配 `FETCH_HTTP_PROXY` |
| 429 带 JSON `code` | App 侧 | 配额用尽 / 队列满 / 被限流，按 `Retry-After` 退避 |
| 429 是 HTML 错误页 | nginx 限流 | 没有 `Retry-After`，按固定间隔退避，别当业务错误展示 |
| `/internal/...` 从公网访问 403 | —— | **这是设计如此**，`/internal/*` 是 `deny all`，必须从容器内打 |

### 6.2 改了配置没生效

按这个顺序排查，基本能覆盖全部情况：

1. **用了 `restart` 吗？** `docker compose restart` 不重新读 `.env`。要重建。
2. **点名了服务吗？** `up -d --force-recreate opencode-1 opencode-2 opencode-3` 不会动 gateway。
   改 `.env` 用不点名的 `up -d`（`./ops.sh apply`）。
3. **改的是镜像里的东西吗？** `opencode.json`、`agents/*.md`、gateway 代码需要 `--build`，
   `--force-recreate` 不够。
4. **改的是 `nginx.conf` 吗？** 单文件 bind mount，`reload` 看不到新内容，必须
   `--force-recreate nginx`。
5. 还是没生效，看容器里到底注入了什么：

```bash
docker compose exec gateway printenv MODEL_NAME        # 进程拿到的值
docker compose exec opencode-1 printenv MODEL_BASE_URL # 实例拿到的值
docker compose exec nginx sha256sum /etc/nginx/nginx.conf   # 与宿主机 nginx.conf 对比
```

### 6.3 站点整体 502 / 打不开

| 症状 | 原因 |
|---|---|
| 改完 `nginx.conf` 后全站 502 | 配置写错或容器读到旧内容。`docker compose exec nginx nginx -t` 验语法 |
| 重建 gateway 后全站 502，过十几秒自愈 | 这是**已知并已修**的场景：nginx 用「变量 + `resolver`」按 10 秒重新解析 gateway 名字。最多 10 秒自愈，不是故障 |
| nginx 容器起不来 | 证书缺失。`nginx.conf` 强制 TLS，`certs/fullchain.pem` 和 `certs/privkey.pem` 必须存在 |
| 全站 502 且 nginx 日志有 `unknown directive "﻿#"` | 配置文件被写入了 UTF-8 BOM，用无 BOM 方式重写 |

### 6.4 容器健康状态不对

```bash
./ops.sh heal        # 只重建不健康的容器
```

| 容器 | 探针打的是 | 说明 |
|---|---|---|
| `nginx` | 自己的 `/healthz` | 刻意不代理到 gateway：否则网关一挂会把 nginx 也判成不健康 |
| `gateway` | `/api/v1/health` | |
| `opencode-N` | `/session`（带 basic auth） | 不是 `/global/health`——那个不触发 bootstrap，配置坏了照样 200 |
| `mock-model` | `/health` | |

> **`engine: ready` 不代表模型可用。** 网关只探 opencode 实例的活性，不探模型。
> mock-model 挂掉时 opencode 依旧 healthy，要等第一个任务失败才暴露。
> 所以 `docker compose ps` 里请确认 `agent-mock-model` 也是 `healthy`。

### 6.5 部署相关的其他坑

见 `deploy/README.md` 第 3 节（构建顺序、改完配置要重建）、第 12 节（国内网络）、
第 14 节（重启语义、健康探针分层、宿主机重启后自动恢复）。

### 7.3 本地开发

### 7.4 两种「模拟」，别搞混

| 开关 | 走的路径 | 用途 |
|---|---|---|
| `MOCK_MODE=true` | 网关直接造假 agent，**不启动 opencode 客户端** | App 侧快速对接口、SSE、配额 |
| `MOCK_MODE=false` + `MODEL_BASE_URL` 指向 `mock-model` | 网关 → opencode → mock-model | 验证整条链路（`.env.example` 的默认） |

差别不只是快慢：`MOCK_MODE=true` 时 opencode 与 mock-model 都在空转，
**webfetch 根本不会发生**，所以 url 任务的 `fetched_chars` 恒为 `null`。
要验证抓取与 `source` 字段就必须用 `MOCK_MODE=false`。

### 7.5 模拟覆盖不到、上线前必须真机验证的项

| 模拟下测不出来 | 原因 |
|---|---|
| 模型凭据 / 地址是否可用 | mock-model 不校验 `MODEL_API_KEY`，写错也能过（错 key 返回 200） |
| `usage` 里的 tokens 与 cost | mock 的数字是编造的，**不要拿它做预算或计费** |
| 任务超时回收（180s） | 模拟任务 1~2 秒就结束，永远到不了超时 |
| 抓取失败的处理 | 模拟下 webfetch 永远成功 |
| 排队积压与并发 | 模拟太快，压不出队列 |
| 模型多轮工具调用 | mock 只做一轮（先抓一次，再给摘要） |
